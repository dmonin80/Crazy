Ты — ведущий разработчик настольных приложений, системный аналитик и архитектор баз данных. Разработай полноценную программу инвентаризации имущества для Windows с русскоязычным интерфейсом.

Нужна программа для реальной эксплуатации: с исходным кодом, серверной и клиентской частями, базой данных, сборкой для Windows, инструкциями, резервным копированием и проверкой основных сценариев.

Не ограничивайся макетом интерфейса или демонстрационным прототипом.

# 1. Назначение программы

Первоначальным источником данных является выгрузка из 1С. Она определяет исходную номенклатуру и начальное количество имущества.

После первого импорта всё имущество поступает на специальный системный «Нулевой склад».

Далее пользователи распределяют имущество с Нулевого склада по другим складам и подскладам, назначают ответственных лиц, указывают размещение и реквизиты документов.

Учёт распределённого имущества — поштучный: каждая единица получает отдельную карточку и собственный инвентарный номер.

Программа должна поддерживать:

- импорт исходной номенклатуры из 1С;
- распределение имущества;
- перемещения и возвраты;
- контроль остатков;
- справочники;
- одновременную работу нескольких пользователей;
- фактическую инвентаризацию;
- печать этикеток с инвентарным номером и QR-кодом;
- поиск карточки по QR-коду;
- использование сканера при проверке имущества;
- фильтры по принципу Excel;
- экспорт в Excel;
- служебный журнал действий;
- резервное копирование;
- перенос программы вместе с данными на другой компьютер.

Обязательные принципы:

- Наименование номенклатуры строго соответствует исходной выгрузке из 1С.
- Исходный код из 1С сохраняется без изменений.
- Пользователь может добавлять к исходному коду суффикс инвентарного номера.
- Нельзя распределить больше имущества, чем доступно на складе-источнике.
- Все движения проходят через сервер и сохраняются в истории.
- Каждая индивидуальная единица одновременно находится только в одном месте.
- Все постоянные серверные данные находятся в папке программы.
- Интернет для основных функций не требуется.

# 2. Платформа и технологии

Программа предназначена для Windows 11.

Предпочтительный стек:

- Python;
- PySide6 — настольный интерфейс;
- FastAPI — серверная часть;
- SQLite — база данных;
- openpyxl — импорт и экспорт XLSX;
- библиотека формирования QR-кодов;
- средства формирования PDF и печати;
- PyInstaller — сборка для Windows.

Предпочтительная версия Python — 3.14.

Совместимость зависимостей с выбранной версией Python проверить фактически. Если компонент несовместим, явно сообщить об этом и предложить рабочее решение.

Не заявлять об успешной сборке, совместимости или проверке без выполнения соответствующих действий.

Фиксировать версии зависимостей.

# 3. Архитектура многопользовательской работы

Реализовать архитектуру «сервер — настольные клиенты».

Сервер:

- работает на одном компьютере в локальной сети;
- хранит базу;
- проверяет права;
- контролирует остатки;
- проводит операции;
- обеспечивает поиск;
- сохраняет историю и аудит;
- обслуживает клиентские приложения.

Клиент:

- работает на компьютере пользователя;
- подключается к серверу;
- показывает данные;
- отправляет команды;
- печатает документы и этикетки на доступных пользователю принтерах;
- принимает ввод от сканера.

Клиент не должен открывать SQLite напрямую.

Запрещено организовывать многопользовательскую работу через прямое открытие общего файла SQLite несколькими клиентами из сетевой папки.

Все изменения проходят через сервер.

На компьютере сервера также можно запускать клиент.

Для одного пользователя сервер и клиент могут находиться на одном компьютере.

Сервер продолжает работу после закрытия клиентского приложения.

Предусмотреть автоматический запуск сервера средствами Windows и инструкцию настройки.

Настройки подключения клиента:

- адрес;
- порт;
- параметры соединения;
- проверка доступности сервера.

Предусмотреть документированный способ настройки HTTPS и доверия к сертификату. Не отключать проверку сертификатов глобально.

# 4. Хранение данных и перенос

Пользователь выбирает папку установки.

Внутри папки серверной части хранить:

- базу;
- настройки;
- резервные копии;
- исходные импортированные файлы;
- журналы;
- шаблоны этикеток;
- другие постоянные файлы.

Постоянные клиентские настройки хранить в папке клиента.

Не хранить базу и постоянные настройки в AppData или реестре Windows.

Для внутренних данных использовать относительные пути.

Проверять права записи в выбранную папку.

Перенос сервера:

1. Корректно остановить сервер.
2. Скопировать всю папку на другой компьютер.
3. Запустить сервер.
4. При изменении адреса обновить настройки клиентов.
5. При необходимости заново настроить автозапуск и сетевой доступ.

После переноса должны сохраняться:

- номенклатура;
- индивидуальные карточки;
- остатки;
- склады;
- справочники;
- пользователи и пароли;
- документы;
- история;
- инвентаризации;
- шаблоны этикеток;
- идентификаторы QR-кодов.

Ранее напечатанные QR-коды должны продолжать работать после переноса.

Готовая сборка не должна требовать установки Python на целевом компьютере.

# 5. Импорт выгрузки из 1С

Основной формат — XLSX.

Дополнительно поддержать CSV с выбором кодировки и разделителя.

Архитектура импорта должна позволять добавлять XLS и другие форматы, которые фактически выдаёт 1С.

Неподдерживаемый формат определять и показывать понятное сообщение. Не читать XLS как XLSX.

Из файла использовать только:

1. Номенклатура.
2. Код.
3. Единица измерения.
4. Количество.

Остальные колонки не переносить в учётную модель.

## 5.1. Мастер импорта

Предусмотреть:

- выбор файла;
- выбор листа;
- выбор строки заголовков;
- сопоставление колонок;
- предварительный просмотр;
- проверку данных;
- отчёт об ошибках;
- подтверждение.

Не предполагать, что заголовки всегда расположены в первой строке.

Допускать варианты названий заголовков через сопоставление, например «Ед. изм.» и «Единица измерений».

## 5.2. Наименование

Сохранять строго как в исходном файле:

- без исправления написания;
- без смены регистра;
- без сокращений;
- без замены символов;
- без удаления значимых пробелов.

Для поиска можно использовать отдельное производное представление, не изменяющее исходное значение.

## 5.3. Код

Хранить как текст.

Сохранять:

- ведущие нули;
- буквы;
- разделители;
- точную последовательность символов.

Не преобразовывать код в научную запись и не округлять.

Учитывать числовой формат Excel, если он однозначно задаёт ведущие нули.

Если исходный файл уже утратил часть кода, не угадывать её. Показать предупреждение.

## 5.4. Количество

На этапе чтения использовать точную десятичную арифметику.

Для поштучного учёта принимать только целые неотрицательные значения.

Дробные значения:

- не округлять;
- выводить на проверку;
- не преобразовывать автоматически в штуки.

Не считать разные единицы измерения взаимозаменяемыми.

Пустые обязательные поля, отрицательные и некорректные количества считать ошибками.

Строки итогов, пустые строки и дополнительные заголовки не создавать как номенклатуру.

Формулы не выполнять. Если отсутствует сохранённый результат формулы в обязательном поле, предложить пересохранить файл с рассчитанными значениями.

## 5.5. Повторяющиеся коды

При повторении кода:

- выявлять дубли;
- при разных наименованиях или единицах измерения блокировать конфликт;
- при одинаковых реквизитах предлагать объединение количества;
- объединять только после подтверждения;
- сохранять связь с исходными строками.

Одинаковое наименование при разных кодах не является основанием для объединения.

## 5.6. Подтверждение

Показывать:

- количество позиций;
- общее количество единиц;
- ошибки;
- предупреждения;
- предлагаемые объединения.

Для ошибки указывать строку и причину.

Первый импорт выполнять атомарно.

Сохранять:

- исходный файл;
- его имя и контрольную сумму;
- пользователя;
- дату и время;
- результат импорта;
- количество позиций и единиц.

Первый подтверждённый импорт создаёт номенклатуру и начальные остатки Нулевого склада.

# 6. Повторная выгрузка из 1С

Повторная загрузка не должна автоматически увеличивать остатки.

Обнаруживать загрузку того же файла.

На первом этапе повторный импорт используется для сравнения:

- новые коды;
- отсутствующие коды;
- изменения наименований;
- изменения единиц измерения;
- изменения количества.

Показывать отчёт.

Не удалять имущество из-за отсутствия позиции в новой выгрузке.

Не перезаписывать автоматически карточки, наименования и остатки.

Применение новой выгрузки к существующему учёту требует отдельного согласованного механизма. До его согласования повторный импорт не изменяет данные.

# 7. Учётная модель

Разделить сущности:

- база учёта;
- импорт;
- номенклатура;
- начальный запас;
- индивидуальная единица имущества;
- текущее размещение;
- документ движения;
- строки документа;
- инвентаризационная сессия;
- результат проверки;
- неопознанная находка;
- шаблон этикетки;
- задание формирования или печати этикеток;
- событие аудита.

Использовать постоянные внутренние идентификаторы.

Наименование, местоположение и инвентарный номер не использовать как первичные ключи.

База учёта должна иметь собственный постоянный UUID, сохраняющийся при резервном копировании и переносе.

## 7.1. Номенклатура

Хранить:

- внутренний ID;
- исходный код;
- исходное наименование;
- единицу измерения;
- начальное количество;
- связь с импортом.

Исходные реквизиты нельзя менять в рабочих таблицах.

## 7.2. Нулевой склад

Раздельно учитывать:

- нераспределённые единицы без индивидуальных карточек;
- возвращённые единицы с уже присвоенными номерами.

Для каждой номенклатуры показывать:

- начальное количество;
- неиндивидуализированный остаток;
- возвращённые единицы;
- количество на других складах;
- доступный остаток Нулевого склада.

Возврат не уничтожает карточку и не освобождает номер.

# 8. Поштучный учёт

Каждая распределённая единица имеет:

- постоянный внутренний ID;
- связь с номенклатурой;
- индивидуальный инвентарный номер;
- количество 1;
- место размещения;
- ответственного;
- дополнительные реквизиты;
- историю;
- постоянную идентичность для QR-кода.

Пример:

Из 1С импортированы 20 стульев с кодом `00001234`.

При распределении 5 стульев:

- создаются 5 карточек;
- каждой присваивается собственный номер;
- каждая содержит количество 1;
- на Нулевом складе остаётся 15 нераспределённых единиц.

Поддержать:

- массовое создание;
- общие реквизиты для группы;
- индивидуальное уточнение;
- групповое перемещение.

В поштучном режиме одна строка — одна единица.

Дополнительно реализовать сводный режим по:

- номенклатуре;
- объекту;
- кабинету;
- ответственному.

В сводном режиме количество равно числу единиц группы.

Не смешивать сводные итоги с индивидуальными строками так, чтобы возникал двойной подсчёт.

# 9. Инвентарные номера

Номер:

неизменяемый код из 1С + обязательный суффикс.

Пример: `00001234/0001`.

Исходную часть нельзя изменять.

Суффикс хранить отдельно.

Полный номер уникален во всей базе, включая ранее использованные номера.

Способы задания:

- вручную;
- автоматическая последовательная генерация.

Для автоматической генерации:

- настраиваемый формат;
- предварительный просмотр;
- серверная проверка;
- защита от совпадений при одновременной работе.

Номер сохраняется при перемещении, возврате и смене ответственного.

Исправление номера после создания разрешать только уполномоченному пользователю:

- с указанием причины;
- с сохранением старого номера;
- с аудитом;
- с уведомлением о необходимости заменить этикетку.

Смена номера не должна менять внутренний ID или идентичность QR-кода.

# 10. Склады и подсклады

Пользователь создаёт названия вручную.

Иерархия первой версии:

- склад;
- подсклад.

Предварительное назначение:

- склад — объект, здание или площадка;
- подсклад — кабинет или место хранения.

Разрешить размещение непосредственно на складе.

Подсклад принадлежит одному складу.

Запретить:

- удаление Нулевого склада;
- удаление склада с остатками;
- удаление склада с подскладами;
- назначение подсклада другого объекта.

Использованные записи архивировать.

Переименование не должно разрушать историю. Документы сохраняют сведения, действовавшие на момент операции.

# 11. Перемещения и контроль остатков

Реализовать:

- распределение с Нулевого склада;
- возврат;
- движение между складами;
- движение между подскладами;
- смену ответственного;
- исправление ошибочного движения.

При первом распределении задаётся количество и создаются карточки.

При дальнейших перемещениях выбираются существующие единицы.

Реквизиты операции:

- источник;
- назначение;
- выбранное имущество;
- количество;
- ответственный;
- дата документа;
- номер документа;
- комментарий.

Проведение атомарно:

1. Проверяет права.
2. Проверяет актуальное наличие.
3. Проверяет назначение.
4. Создаёт документ.
5. Создаёт или перемещает карточки.
6. Обновляет остатки.
7. Записывает аудит.

Не допускать отрицательных остатков.

Если на складе 10 единиц, а два пользователя одновременно запрашивают по 7, успешно проходит только одна операция.

Проверки выполняются сервером внутри транзакции.

Редактирование таблицы не должно обходить документы движения.

Проведённые документы не переписывать и не удалять.

Исправления оформлять связанными операциями. Учитывать последующие движения при попытке отмены.

Без дополнительного согласования не реализовывать списание и дополнительные поступления.

При отсутствии поступлений и списаний:

начальное количество = неиндивидуализированный остаток Нулевого склада + количество всех индивидуальных карточек.

Каждая карточка имеет ровно одно текущее место размещения.

# 12. Основное рабочее окно

Ориентироваться на предоставленный образец таблицы.

Интерфейс должен быть читаемым, русскоязычным и удобным для ежедневной работы.

Колонки:

1. «Наименование» — строго из выгрузки, без ручного изменения.
2. «Инвентарный номер» — код с суффиксом.
3. «Общее количество» — 1 в поштучном режиме, число единиц в сводном.
4. «Объект» — основной склад.
5. «Этаж» — ручное текстовое поле: «1», «цоколь», «технический».
6. «Кабинет» — подсклад выбранного объекта.
7. «Ответственное лицо» — выпадающий список с поиском.
8. «Наименование склада» — автоматически сформированный путь «Объект / Подсклад».
9. «Примечание» — ручной комментарий.
10. «Поставщик» — выпадающий список с поиском.
11. «Дата документа» — выбор через календарь.
12. «Номер документа» — текст с сохранением ведущих нулей и символов.

Если подсклад не указан, «Наименование склада» содержит основной склад.

Не делать это поле независимым ручным текстом, противоречащим размещению.

В основной таблице дата и номер документа — реквизиты последнего проведённого движения единицы.

Предыдущие документы сохраняются в истории.

Реквизиты первоначального поступления, если понадобятся, хранить отдельно.

Дополнительные включаемые колонки:

- единица измерения;
- внутренний ID;
- дата последней проверки;
- результат последней проверки;
- дата последнего формирования этикетки;
- признак необходимости замены этикетки.

Не называть дату отправки задания на принтер подтверждением физического наклеивания этикетки.

# 13. Работа с таблицами

Предусмотреть:

- изменение ширины и порядка колонок;
- скрытие колонок;
- закреплённые заголовки;
- сортировку;
- поиск;
- множественное выделение;
- копирование;
- карточку имущества;
- массовые операции;
- сохранение персонального вида.

Показывать:

- число найденных строк;
- число выбранных единиц;
- активные фильтры;
- пользователя;
- состояние подключения.

Поиск работает по полному набору данных.

Обновление не должно без необходимости сбрасывать выделение и прокрутку.

Изменения реквизитов сохранять явно.

При закрытии с несохранёнными изменениями предлагать сохранение или отмену.

Поддержать клавиатуру и стандартные сочетания при русской и английской раскладках.

Основные команды:

- «Нулевой склад»;
- «Переместить»;
- «Вернуть»;
- «Инвентаризация»;
- «Печать этикеток»;
- «Найти по QR-коду»;
- «Экспорт в Excel»;
- «Справочники»;
- «Настройки» в рамках прав.

# 14. Фильтры по принципу Excel

- поиск по значениям;
- уникальные значения с флажками;
- выбрать всё;
- снять всё;
- пустые;
- непустые;

- содержит;
- не содержит;
- начинается с;
- заканчивается на.

- не равно;

Для дат:

- конкретная дата;

- диапазон.

Предусмотреть:

- персональное сохранение.

В сводном режиме явно показывать, что фильтруются и экспортируются группы.

# 15. Экспорт в Excel

Учитывать:

- фильтры;
- сортировку;
- колонки;
- порядок;
- поштучный или сводный режим.

Экспортировать все подходящие строки, а не только видимую страницу.

Дополнительно:

- экспорт выделенного;
- экспорт всех доступных данных.

Перед экспортом показывать режим и объём.

XLSX должен содержать:

- заголовки;
- читаемые размеры;
- закреплённую строку;
- автофильтр;
- корректные даты;
- числовые количества;
- текстовые коды и номера.

Пользовательский текст записывать безопасно как текст, не как формулы.

Отдельный лист содержит:

- время;
- пользователя;
- режим;
- фильтры;
- количество строк и единиц.

Экспортировать согласованное состояние данных.

Служебный журнал не включать в обычную выгрузку имущества.

# 16. Справочники

Реализовать:

- склады;
- подсклады;
- ответственные лица;
- поставщики;

Операции:

- создание;
- редактирование;
- поиск;
- архивирование;
- предупреждение о возможных дублях.

Ответственное лицо и пользователь — разные сущности.

Ответственный не обязан иметь учётную запись.

ФИО не считать уникальным ключом.

Для ответственного предусмотреть ФИО и необязательное подразделение.

Для поставщика — наименование и необязательные идентифицирующие реквизиты.

Использованные записи не удалять физически.

# 17. Этикетки с инвентарным номером и QR-кодом

Печать этикеток — обязательная функция первой версии.

Для каждой индивидуальной единицы должна формироваться этикетка, позволяющая:

- прочитать номер без сканера;
- найти карточку по QR-коду;
- быстро отметить имущество при инвентаризации.

## 17.1. Состав этикетки

Обязательные элементы:

- полный инвентарный номер;
- QR-код.

Дополнительные настраиваемые элементы:

- краткое отображение наименования;
- организация;
- объект;
- кабинет;
- небольшой логотип.

Сокращение наименования допустимо только при отображении на этикетке. Исходное наименование в базе остаётся неизменным.

По умолчанию не размещать на этикетке изменяемые сведения о размещении и ответственном, чтобы перемещение не требовало обязательной перепечатки.

Если такие поля включены в шаблон, после их изменения показывать рекомендацию заменить этикетку.

Номер должен оставаться читаемым при выбранном размере.

Не обрезать длинный номер молча. Предусмотреть перенос, допустимое изменение шрифта или предупреждение о слишком маленьком шаблоне.

## 17.2. Содержимое QR-кода

QR-код должен содержать стабильный технический идентификатор, а не изменяемые сведения.

Использовать версионированный формат, например:

`INV1:<UUID_базы>:<UUID_единицы>`

Допускается другой документированный формат с теми же свойствами.

Обязательные требования:

- постоянный ID единицы;
- идентификатор базы;
- версия формата;
- отсутствие зависимости от IP и пути установки;
- отсутствие ФИО, паролей, токенов и других персональных или секретных данных;
- работа после переноса папки сервера;
- сохранение связи после исправления отображаемого номера.

QR-код не является разрешением на доступ. Права проверяются после поиска карточки.

Не привязывать основной QR-код к текущему HTTP-адресу сервера.

После восстановления резервной копии прежние этикетки должны находить те же карточки.

## 17.3. Шаблоны

Реализовать настройку шаблонов.

Поддержать:

- отдельные этикетки на термопринтере;
- листы A4 с несколькими этикетками.

Параметры:

- ширина и высота в миллиметрах;
- ориентация;
- поля;
- размер QR-кода;
- размер шрифта;
- расположение элементов;
- количество строк и колонок для A4;
- горизонтальные и вертикальные интервалы;
- отступы листа.

Предусмотреть стартовые шаблоны распространённых размеров, например:

- 40 × 30 мм;
- 58 × 40 мм;
- настраиваемый лист A4.

Это шаблоны, а не обещание поддержки конкретного принтера без проверки его драйвера и размеров бумаги.

Пользователь может сохранить шаблон под своим названием.

Ограничить редактирование общих шаблонов правами.

## 17.4. Качество QR-кода

Обеспечить:

- чёрный код на белом фоне;
- достаточную свободную зону вокруг;
- отсутствие растяжения;
- отсутствие сглаживания, ухудшающего чтение;
- подходящий размер модуля с учётом разрешения печати;
- отсутствие логотипа поверх кода в базовом варианте.

При слишком маленьком размере показывать предупреждение.

Для PDF по возможности использовать векторное представление.

Если используется растр, формировать его под целевое разрешение без размытия.

Проверить машинное декодирование сформированных кодов.

Физическую читаемость подтвердить тестовой печатью на фактически используемом оборудовании. Не заявлять такую проверку без принтера.

## 17.5. Выбор имущества

Печать доступна:

- из карточки;
- для выделенных единиц;
- для всех единиц текущего фильтра;
- сразу после распределения.

Перед формированием показывать:

- число единиц;
- число копий каждой этикетки;
- итоговое число этикеток;
- шаблон;
- принтер или PDF.

Для сводной строки сначала определить конкретные карточки. Не создавать один QR-код на группу разных единиц.

Для неиндивидуализированного остатка Нулевого склада индивидуальные этикетки не печатать до создания карточек и номеров.

## 17.6. Предварительный просмотр и печать

Реализовать:

- предварительный просмотр;
- выбор принтера;
- выбор формата;
- число копий;
- пробную печать;
- экспорт в PDF;
- повторную печать.

Для A4 предусмотреть начальную позицию на частично использованном листе: пропуск уже занятых ячеек.

Печатать в фактическом размере. Предупреждать, что автоматическое масштабирование драйвера может изменить размеры.

Отправлять задание на принтер клиента, а не только на принтер серверного компьютера.

Повторная печать использует тот же QR-код и не создаёт новую карточку.

Сама печать не меняет остатки и размещение.

## 17.7. Учёт формирования и печати

Фиксировать:

- пользователя;
- дату и время;
- выбранные единицы;
- шаблон и его версию;
- число копий;
- способ вывода;
- доступный результат операции.

Различать:

- PDF сформирован;
- задание передано системе печати;
- ошибка;
- пользователь подтвердил нанесение этикетки, если такая функция реализована.

Не утверждать, что этикетка физически напечатана или наклеена, только по успешной отправке задания.

При исправлении инвентарного номера отмечать необходимость замены старой этикетки. Старый QR-код продолжает указывать на ту же карточку.

# 18. Сканирование и поиск

В первой версии поддержать 2D-сканер QR-кодов, работающий как USB-клавиатура и передающий строку с завершающим Enter.

Поддержка камеры и мобильного телефона — отдельное расширение.

## 18.1. Режим поиска

Предусмотреть отдельное поле или окно «Найти по QR-коду».

После сканирования:

- разобрать формат;
- проверить версию;
- проверить идентификатор базы;
- найти единицу;
- открыть карточку при наличии прав.

Дополнительно разрешить ручной ввод инвентарного номера.

Сканируемый текст не выполнять как команду и не открывать автоматически как произвольный URL.

Не перехватывать все символы во всех полях приложения. Сканирование должно работать в явно активном поле или режиме, чтобы не повреждать комментарии и другие данные.

После обработки возвращать фокус в поле сканирования.

Сообщения:

- код распознан;
- карточка не найдена;
- код другой базы;
- формат не поддерживается;
- нет прав;
- сервер недоступен.

Обычное сканирование для поиска не должно перемещать имущество или отмечать его наличие без выбранной инвентаризационной сессии.

## 18.2. Сканирование при инвентаризации

Внутри активной сессии предусмотреть режим последовательного сканирования.

Два режима:

- показать карточку и запросить подтверждение;
- быстрая отметка наличия.

Быстрый режим пользователь включает явно.

Показывать, в каком объекте и кабинете проводится проверка.

После успешного сканирования допустимо автоматически отметить «В наличии» только если:

- карточка относится к проверяемому составу;
- фактическое место соответствует контексту;
- нет движения или конфликта, требующего проверки;
- у пользователя есть право.

Если имущество относится к другому месту или отсутствует в снимке, показать отдельный сценарий расхождения. Не менять размещение автоматически.

Повторное сканирование той же единицы:

- сообщает «Уже проверено»;
- не увеличивает количество;
- не создаёт дубли результатов.

Неизвестный QR-код не создаёт имущество автоматически.

Для находки использовать отдельную команду регистрации.

Предусмотреть визуальное подтверждение и необязательный звуковой сигнал результата.

# 19. Фактическая инвентаризация

Реализовать отдельный раздел «Инвентаризация».

## 19.1. Сессия

Реквизиты:

- название;
- дата;
- номер документа;
- выбранные объекты и подсклады;
- ответственные при необходимости;
- проверяющие;
- комментарий.

Область проверки:

- всё имущество;
- объект;
- несколько подскладов;
- имущество ответственного.

При начале сохранять снимок состава на определённый момент.

Снимок включает:

- ID единицы;
- номер;
- код;
- наименование;
- учётное размещение;
- ответственного.

Дальнейшие движения и переименования не переписывают снимок.

## 19.2. Проверка

Для единицы показывать:

- наименование;
- инвентарный номер;
- учётное место;
- учётного ответственного;
- результат;
- фактическое место;
- фактического ответственного при отличии;
- комментарий;
- проверившего;
- время;
- способ проверки: вручную или сканированием.

Статусы:

- «Не проверено»;
- «В наличии»;
- «Не найдено»;
- «Обнаружено в другом месте».

«Не проверено» не считать недостачей.

Учётные и фактические значения хранить раздельно.

## 19.3. Находки вне списка

Если имущество отсутствует в составе сессии:

1. Искать его в общей базе.
2. При наличии карточки связать находку с ней.
3. При отсутствии создать запись неопознанной находки.

Хранить описание, обнаруженный номер, место, комментарий и проверяющего.

Не создавать фиктивный код 1С.

Не увеличивать остатки автоматически.

## 19.4. Работа нескольких проверяющих

Поддержать:

- ручной поиск;
- QR-сканирование;
- промежуточное сохранение;
- одновременную проверку;
- контроль конфликтов;
- историю исправлений.

Массовые отметки выполнять только как явные операции с показом количества.

## 19.5. Движения во время проверки

Не запрещать все движения автоматически.

При движении после начала сессии:

- показывать предупреждение;
- сохранять исходный снимок;
- показывать связанное движение;
- требовать проверки результата.

Не классифицировать такую единицу как недостачу автоматически.

## 19.6. Состояния

- «Черновик»;
- «В работе»;
- «Завершена»;
- «Отменена».

Перед завершением показывать непроверенные позиции и расхождения.

Завершённую сессию защищать от редактирования.

Повторное открытие — только уполномоченным пользователем с причиной и аудитом.

## 19.7. Отчёты

Формировать:

- ведомость проверки;
- непроверенные позиции;
- ненайденное имущество;
- имущество в другом месте;
- находки вне состава;
- итоговые расхождения.

Экспорт — XLSX.

Результаты проверки не меняют учёт автоматически.

Подтверждённые исправления выполнять отдельными документами со ссылкой на сессию.

Списание недостачи и оприходование излишков не выполнять без отдельно согласованного механизма.

# 21. Служебный журнал

По умолчанию доступен администратору.

Фиксировать:

- ID события и операции;
- пользователя;
- серверное время;
- действие;
- сущности;
- код;
- номер;
- источник и назначение;
- количество;
- старые и новые значения;
- результат;
- причину;
- клиентский сеанс.

Журналировать:

- импорт;
- движения;
- возвраты;
- смену ответственных;
- изменение реквизитов;
- исправление номеров;
- справочники;
- пользователей;
- экспорт;
- инвентаризации;
- изменения результатов;
- формирование и печать этикеток;
- изменение шаблонов;
- резервное копирование и восстановление.

Для массовой операции сохранять перечень единиц.

Аудит успешного изменения записывать в той же транзакции.

Неуспешные значимые операции фиксировать без ложного движения.

Фильтры журнала:

- пользователь;
- период;
- действие;
- код;
- номер;
- объект.

Журнал не включать в основную рабочую таблицу и обычный экспорт имущества.

Время хранить однозначно, например в UTC, отображать в настроенном часовом поясе.

# 22. Конкурентность и сетевые сбои

Реализовать:

- транзакции;
- ограничения целостности;
- контроль остатков;
- уникальность номеров;
- контроль версий;
- обработку блокировок SQLite.

При конфликте редактирования не затирать чужие изменения.

Показывать конфликт и предлагать обновление.

Каждый запрос изменения имеет уникальный ID.

Повтор запроса не создаёт вторую операцию.

Сервер позволяет проверить результат по ID.

При потере ответа клиент показывает неопределённый результат до проверки, а не предлагает слепо повторить операцию.

При потере соединения:

- обозначать состояние;
- блокировать изменения;
- не создавать скрытую очередь;
- разрешать просмотр загруженных данных с отметкой об их неактуальности.

В первой версии не поддерживать автономное подтверждение инвентаризации без сервера.

После восстановления связи обновлять данные.

# 23. Резервные копии и обновления

Предусмотреть:

- ручную копию;
- расписание;
- срок хранения;
- копию перед импортом;
- копию перед миграцией;
- проверку восстановления.

Использовать согласованный механизм резервного копирования SQLite.

Не ограничиваться копированием открытого файла.

Копия включает необходимые данные, настройки, шаблоны и версии схемы.

При восстановлении:

1. Перейти в режим обслуживания.
2. Остановить изменения.
3. Уведомить клиентов.
4. Проверить архив.
5. Сохранить текущее состояние.
6. Восстановить.
7. Проверить целостность.
8. Возобновить работу.

UUID базы и карточек должны сохраняться, чтобы прежние QR-коды продолжали работать.

Предусмотреть миграции при обновлении.

Не удалять данные при обновлении.

Рекомендовать дополнительную копию на другом носителе.

# 25. Границы первой версии

Обязательны все описанные основные функции, включая:

- поштучный учёт;
- фактическую инвентаризацию;
- печать этикеток;
- QR-коды;
- поиск и проверку сканером в режиме USB-клавиатуры.

- мобильный интерфейс;

- списание;
- дополнительные поступления;
- применение изменений повторной выгрузки из 1С;
- специализированные команды конкретных промышленных принтеров вместо печати через драйвер Windows.

Не заменять основные функции этими расширениями.
