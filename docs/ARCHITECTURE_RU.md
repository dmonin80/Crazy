# АХО: архитектура и проектирование

Документ относится к этапу 0.2.6 (групповой перенос по кнопке и точные дробные количества), а не к завершённой версии по полному ТЗ.

## Понимание задачи

Исходная выгрузка 1С задаёт верхнюю границу количества. Название, код и единица измерения сохраняются в номенклатуре. Первое распределение индивидуализирует часть начального количества. Возврат возвращает существующую карточку на Нулевой склад; он не превращает её в новый нераспределённый остаток. Повторная выгрузка предназначена только для сравнения.

Сервер является единственным владельцем SQLite. Клиент использует HTTP API и не имеет доступа к базе. В штатной эксплуатации в ЛВС следует использовать HTTPS. Интернет для учёта после установки зависимостей не нужен.

## Единый локальный режим 0.2

Один запуск `run_inventory.py` или собранного `AHO_Inventory.exe` запускает локальный сервер и клиент на одном ПК. Сервер работает отдельным фоновым процессом того же приложения; это позволяет сохранять его работу после закрытия клиента. База, импорт и все операции по-прежнему доступны клиенту только через API.

Последовательность: блокировка запуска → чтение локальных настроек → проверка готового сервера этой папки → при необходимости старт дочернего процесса → ожидание `/health` → первоначальная настройка/вход → рабочее окно. Совпадение проверяется по типу приложения, постоянному ID экземпляра и отпечатку пути папки. Копия настроек в другой папке не подключается случайно к исходной работающей базе.

Дочерний процесс удерживает системную файловую блокировку до завершения. Повторные запуски сериализованы. Порт сначала резервируется настоящим сокетом; при занятости выбирается свободный. Сокет передаётся Uvicorn, поэтому сервер не теряет выбранный порт между проверкой и запуском. Файлы блокировок могут оставаться после выхода: операционная система снимает саму блокировку при завершении процесса.

Управляющие маршруты создания первого администратора и остановки включаются только в локальном режиме и требуют случайного секрета из `local_server.json`. В обычном сетевом сервере эти маршруты отсутствуют. Секрет не является паролем пользователя и не используется в QR. Сервер локального режима слушает только IPv4 loopback. Для остановки используется корректное завершение Uvicorn после текущих запросов.

Схема базы в этом обновлении не менялась. Существующая папка `data` используется без повторного импорта. Общая версия приложения — 0.2.0; незавершённые функции учёта версии 0.1 остаются в плане.

## Связи базы

- `imports` → `items`: импорт и исходные строки номенклатуры.
- `items` → `assets`: номенклатура и индивидуальные единицы.
- `locations` → `locations`: один уровень подскладов.
- `locations` → `assets`: ровно одно текущее место карточки.
- `documents` → `lines` → `assets`: неизменяемая история движения с копией состояния до и после.
- `sessions` → `checks` → `assets`: состав проверки, замороженный JSON-снимок, отдельный фактический результат.
- `sessions` → `findings`: неопознанные находки без начисления количества.
- `users` → `tokens`: хеши случайных сеансов, срок действия 8 часов.
- `requests`: уникальный UUID команды, автор, отпечаток содержимого, результат.
- `audit`: события и содержимое операций; запись успешного изменения в общей транзакции.

Остаток не хранится как независимо редактируемое число: `initial - count(assets)` даёт неиндивидуализированный остаток. Возвращённые карточки считаются отдельно по `location = zero`. Свободный остаток Нулевого склада равен сумме этих двух величин.

Модификации используют `BEGIN IMMEDIATE`, таймаут ожидания 15 секунд, ограничения UNIQUE, FOREIGN KEY и оптимистическую версию карточки/результата. Перед изменением сервер проверяет актуальную версию. При отказе вся транзакция откатывается, включая документ и строки.

## Основное окно

Макет реализован в работающем PySide6-клиенте; изображение находится в `examples/main_window.png`.

Сверху: название системы и команды подключения, импорта, складов, распределения, перемещения, возврата, инвентаризации, PDF, XLSX. Далее поиск и таблица. Внизу отдельное поле QR и контекст проверки. Токен живёт только в памяти. Постоянно сохраняется адрес подключения; при необходимости в JSON вручную указывается `ca_file`.

Таблица этапа 0.1 содержит название, номер, количество 1, объект, этаж, кабинет, ответственного, склад и примечание. Полный состав колонок и персональные виды из ТЗ — следующий этап.

## Сценарий распределения

1. Администратор выбирает файл, строку заголовков и четыре колонки.
2. Сервер проверяет значения; показаны число позиций, единиц и ошибки.
3. После подтверждения импорт атомарно создаёт исходные остатки; оригинальный файл сохраняется по SHA-256.
4. Создаются склад и при необходимости подсклад.
5. Оператор выбирает номенклатуру, число новых карточек, назначение и реквизиты.
6. Сервер внутри транзакции проверяет остаток и переданные вручную дополнения, составляет номера как точный исходный код + дополнение, проверяет уникальность и создаёт карточки и документ.
7. Возвращённые карточки повторно выдаются командой «Переместить», а не новым распределением.

## Сценарий инвентаризации

Создание сессии сохраняет снимок карточек выбранного места, включая дочерние подсклады основного склада. В ведомости можно вручную установить результат, указать место и комментарий, зарегистрировать находку и выгрузить XLSX. Для сканирования выбирается точное фактическое место. Быстрый режим включается явно. Он не допускает отметку при другом месте, движении после снимка и повторной проверке. Завершение требует подтверждения и защищает результаты от изменений.

Находки пока хранятся как описание; структурированное связывание находки с карточкой и расширенные реквизиты сессии ещё не реализованы. Проверка не создаёт движений.

## Этикетка

Слева — квадратный QR с белой свободной зоной; справа — инвентарный номер с переносом. Наименование, ФИО и адрес сервера в QR не включаются. Имеются 40×30 мм, 58×40 мм и A4: 3 колонки × 8 строк, ячейка 58×30 мм. В API можно указать копии и пропуск занятых ячеек. В клиенте выбирается размер и путь PDF. Для длинного номера, который не помещается, формирование прерывается с объяснением.

PDF можно открыть стандартным просмотрщиком и напечатать в масштабе 100%. Собственный диалог принтера Windows и редактор шаблонов пока не реализованы. Событие в аудите означает «PDF сформирован»; оно не подтверждает печать и нанесение.

## Допущения

В версии 0.2.1 изучены исходная выгрузка и образец ведомости. Исходная выгрузка имеет поля H/I/K/M, заголовки в строке 1. Ведомость служит образцом рабочего представления и не заменяет исходную выгрузку. Сопоставление по заголовкам остаётся настраиваемым; структура не зашита жёстко. Поддерживаются точные неотрицательные десятичные количества. Штучное целое распределение ограничено 10 000 карточек на строку операции; количественная строка создаёт одну карточку на выбранное количество. С версии 0.2.5 дополнения к коду вводятся вручную для каждой единицы; разделитель не добавляется автоматически. Ответственные и поставщики теперь выбираются из справочников по постоянным ID; их отображаемые подписи входят в снимки новых документов. Настройка первого администратора в едином режиме выполняется в окне программы; для дополнительного отдельного сервера сохраняется консольная команда. Блокирующих вопросов для этого этапа нет.

## Импорт 0.2.1

Маршрут `/imports/inspect` возвращает реальные заголовки, предполагаемое сопоставление и строки предпросмотра. `/imports/preview` и `/imports/commit` повторно проверяют выбранные параметры на сервере. Номера `excluded_rows` проверяются на допустимость, сохраняются в аудите вместе с запросом и не меняют архивный файл. Кнопка проведения блокируется при изменении настроек до новой проверки. Необязательные колонки файла не участвуют в модели и их формулы не блокируют импорт. Служебные строки распознаются только по явным признакам; неполная карточка с кодом не считается итогом.

## Нулевой склад 0.2.2

В основной форме два представления: общий остаток номенклатуры и индивидуальные карточки. Строки остатков связываются с внутренним ID номенклатуры, поэтому сортировка и поиск не меняют выбранную позицию. Перед открытием операции остаток запрашивается заново. Диалог ограничивает подсклады выбранным родителем и проводит либо `/allocate` для нераспределённого количества, либо `/move` для явно отмеченных возвращённых карточек. Серверная модель и схема базы не изменены. После подтверждённого проведения обновляются обе таблицы. Потерянный ответ проверяется по ID исходного запроса, повторное нажатие не создаёт новую операцию.

## Справочники 0.2.3

Схема 2 добавляет таблицы `responsibles` и `suppliers` с ID, именем, дополнительными сведениями, архивным признаком и версией. `assets` получает `responsible_id`, `supplier_id` и резервное текстовое поле поставщика; прежнее текстовое поле ответственного сохраняется для совместимости и старой истории. В `locations` добавляется версия. Миграция выполняется в одной транзакции после Backup API-копии существующей базы; повторный запуск не переносит данные заново. Старые строковые значения ответственных связываются с отдельными записями без изменения исходной строки.

`/catalogs` даёт данные для выбора; `/catalogs/{kind}` и `/catalogs/{kind}/{id}` создают и изменяют записи только по правам администратора и с UUID команды. Старые и новые значения изменения включаются в аудит. Структурные имена SQL-таблиц выбираются из закрытого набора; пользовательские значения передаются параметрами.

Новые назначения проходят серверную проверку существования и активности ссылок. Ранее назначенная архивная запись сохраняется при движении без переназначения. Устаревшая версия справочника отклоняется. Нулевой склад не изменяется, склад с остатками или активными подскладами не архивируется. Редактирование не меняет постоянный ID. Отображаемые текущие подписи выбираются соединением со справочником; новые документы и сессии сохраняют собственные подписи на момент операции. Старые документы не переписываются.

Единицы измерения читаются из импортированной номенклатуры; ручной справочник не подменяет единицу 1С. Номенклатура, код и остатки не изменяются через справочники. Права пользователей и ответственные лица остаются разными сущностями.

## Этаж 0.2.4

Команда движения принимает текстовый `floor` и сохраняет его в той же транзакции, что размещение и история. Обе формы отправляют это поле и при создании, и при движении существующих единиц. Явная пустая строка очищает этаж. Для совместимости старого API отсутствие ключа `floor` при движении сохраняет прежнее значение. Схема 2 уже содержит поле, новая миграция не нужна. История `before_json` / `after_json` и аудит содержат применённое значение; ID и инвентарный номер не меняются.

## Ручные номера и переключение представлений 0.2.5

`/allocate` принимает обязательный массив `suffixes` ровно из `quantity` непустых строк. Каждая строка — точное добавление к исходному коду, включая разделитель по желанию пользователя. Нет генерации последовательности и автоматического разделителя. Номера проверяются на повторение в одной команде и во всей базе внутри `BEGIN IMMEDIATE`, затем защищаются UNIQUE-ограничением. При конфликте вся операция откатывается. Старые карточки и их поле `number` не пересчитываются; прежняя запись `suffix` могла хранить только цифры без разделителя, а новые записи хранят введённое дополнение целиком. Для отображения и печати всегда используется сохранённый полный `number`.

`view_switcher.py` содержит две крупные кнопки с единым активным представлением. Компонент располагается над панелью команд, дополнительной команды Нулевого склада в панели нет. Источник строк, поиск и экспорт используют выбранное представление.

## Количества и групповой перенос 0.2.6

Схема 3 добавляет `items.initial_decimal TEXT`, `items.tracking_mode` и `assets.quantity_decimal TEXT`. Эти десятичные строки — авторитетные количественные значения; поле `items.initial` оставлено для совместимости, его нельзя использовать для новых расчётов. Нормализация ввода и точные операции находятся в `quantities.py`: Decimal, до 30 знаков в целой / дробной части, контекст вычислений 100 знаков. Итоги не вычисляются SQLite REAL / SUM над вещественными значениями. JSON возвращает целые как int, дробные — канонической строкой. Интерфейс сортирует числовые колонки через Decimal, а не лексикографически.

Инвариант: начальное количество = неиндивидуализированный остаток + сумма количеств всех карточек. Возвращённый остаток = сумма количеств карточек в zero. Частичный перенос уменьшает количество исходной карточки и создаёт карточку части, с двумя строками истории в одном документе. Идентичность остатка сохраняется, у части новый ID и ручное дополнение. Откат транзакции отменяет оба изменения.

`/batch-transfer` принимает общие реквизиты и до 500 разных наименований. Для каждой строки задаётся количество новых карточек / партии либо возвращённые ID с версиями. Один документ создаётся до обработки строк, все проверки и изменения выполняются в одной транзакции `mutate`. Повтор UUID возвращает прежний результат. Кнопка «Переместить» собирает выделенные ID; обработчиков открытия операции на событиях клика строк больше нет.

`batch_dialog.py` задаёт одно назначение и использует встроенные редакторы выбранных наименований. `quantity_widgets.py` содержит точный ввод количества и числовую сортировку. Основная таблица и экспорт используют реальное количество карточек. Excel-числа с более чем 15 значащими цифрами сохраняются текстом для защиты точности.
